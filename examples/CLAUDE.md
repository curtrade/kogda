# Правила для Claude

Работаем по циклу К-О-Г-Д-А: Контекст → Ограничения → Гипотеза → Дифф → Автотесты.
Как цикл настроен в Claude Code (ворота на коммит, Stop-хук проверок), описано в `docs/workflow.md`.


## К — Контекст

- Задача продолжает начатую работу? Найди её спецификацию и план в `docs/superpowers/` и работай
  по ним.
- Разведку большой кодовой базы отдавай субагенту Explore, в основной контекст бери только выводы.
- Ресёрч в интернете веди через Tavily MCP (`tavily_search`, `tavily_extract`), а не через
  встроенный WebSearch. Запросы отправляй по одному. При ошибке 429 подожди и повтори.
- Скиллы по стеку загружай до первой строки кода:
  - **NestJS:** базовый `/nestjs-builder` или `/nestjs-expert` (по задаче), поверх него
    `/nestjs-configify` (пакет `@itgorillaz/configify`, а не `@nestjs/config`) и `/nestjs-prisma`
    (Prisma, а не Mongoose, TypeORM или другие ORM).
  - **Next.js:** `/next-best-practices`, `/react-best-practices`, `/frontend-design`, `/ui-ux-pro-max`.
  - **Любой другой фронтенд** (HTML, Vite, Astro и т. п.): минимум `/frontend-design` и `/ui-ux-pro-max`.

## О — Ограничения

- Делай только задачу. Проблему, которую заметил вне задачи, опиши в ответе, а не чини молча.
- Не делай проверки зелёными за счёт их ослабления. Без моего согласия не удаляй тесты и не
  переписывай их ожидания под текущее поведение, не добавляй `.skip`, `.only`, `eslint-disable`,
  `@ts-ignore`, `as any`, пустой `catch`.
- Внешние действия — `git push`, деплой, публикация, отправка сообщений, вызовы платных API —
  выполняй только по моей прямой просьбе в этом разговоре.
- Скрипт, который вызывает `claude -p` для задачи без инструментов, запускай с флагами
  `--safe-mode --tools ''`. Без них в каждый вызов попадают CLAUDE.md, хуки и плагины: вызов
  выходит в 36 раз дороже, а правила отсюда протекают в генерацию.

## Г — Гипотеза

- Если правка затрагивает несколько файлов или подход неочевиден, начни со спецификации и плана:
  superpowers `brainstorming` → `writing-plans`. Спецификации клади в `docs/superpowers/specs/`,
  планы — в `docs/superpowers/plans/`. Если дифф описывается одним предложением, делай сразу.
- В спецификации должны быть: какие файлы и интерфейсы меняются, раздел «Вне задачи» и проверка,
  которая доказывает, что результат работает целиком.
- Режь план так, чтобы одна задача давала один коммит, а её дифф читался за 5–10 минут.

## Д — Дифф

- Коммить после каждой законченной задачи, не дожидаясь просьбы. `git commit` ждёт моего
  подтверждения: это передача черновика на ревью.
- Перед `git commit` напиши в одном сообщении:
  - что сделано и зачем;
  - какие файлы изменены (`git diff --stat`);
  - что изменилось в тестах, особенно удалённые или переписанные проверки;
  - подавления ошибок, новые зависимости, правки конфигов, если они есть;
  - на что смотреть в первую очередь.
- Если я отклонил коммит, не повторяй его, пока не исправишь по замечанию. Ворота не обходи:
  не коммить через скрипты, алиасы и другие обходные команды.
- Не переписывай историю уже принятых коммитов (`--amend`, `rebase`, `reset`) без моей просьбы.
- Коммиты создавай **без** строки `Co-Authored-By`.

## А — Автотесты

- Код пиши по TDD: сначала тест, убедись, что он падает по нужной причине, потом реализация,
  потом рефакторинг.
- В новом проекте подключай ESLint и Prettier с первого коммита.
- Stop-хук в конце хода гоняет tsc, eslint, `vitest related` и pytest по файлам, которые ты
  изменил, и не даёт закончить ход, пока они красные. Если падение вызвано твоими правками,
  исправь. Если оно не связано с задачей (старый долг, нет базы, окружение), не чини чужое:
  скажи мне, что упало и почему, и заверши ход.
- Говори «готово» только с доказательством: команда и её вывод, сколько тестов прошло.
- Хук не ловит e2e, сборку и ошибки типов в файлах, которые ты сломал через импорт. Поэтому
  перед слиянием ветки сделай полный прогон: весь tsc, все тесты, e2e, `build`. Если основная
  ветка уже красная, сравни с ней и покажи, что новых падений нет.
